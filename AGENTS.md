## RCKT Foundation Governance Contract

### Source of Truth
- **GitHub** is the single source of truth for all project state
- Every change must flow through Git
- Lovable Cloud synchronizes commits on the currently connected branch
- RCKT organizational policy: `design/*` for Lovable visual work, `feature/*` for Claude Code architecture/backend

### Lovable ↔ Claude Code Separation

**Lovable Cloud owns:**
- Visual design and layout
- Responsive behavior (mobile/tablet/desktop)
- Animations and micro-interactions
- Asset management (images, icons)
- Presentational components
- Approved copy and text content

**Claude Code owns:**
- Project architecture and structure
- Server routes in TanStack Start (`src/routes/api/*`)
- Server-side integrations (OpenRouter, Supabase service role)
- Database migrations and RLS policies
- CI/CD pipeline
- Deployment configuration (Render)
- Type contracts and API design
- Security and secrets management
- Metrics and observability

**Shared responsibility:**
- This governance document (AGENTS.md)
- README and essential docs
- Type definitions and contracts
- Bug fixes (coordinated via branches)

### Branch Policy

**Branch Structure:**
- `main` — stable integration branch; protection rules recommended and TBD in GitHub settings
- `design/*` — Lovable Cloud edits (design/animations/copy iterations)
- `feature/*` — Claude Code features (architecture, backend, integrations)
- `fix/*` — bug fixes (either team)

**Rules:**
- One feature/fix per branch; do not work simultaneously on the same branch
- Merge only via Pull Request with review
- No `force push` under any circumstances
- No `git rebase`, `git amend`, or `git commit --squash` of commits already pushed by Lovable Cloud
- All history is linear and immutable

### Lovable Cloud Commits
- Commits pushed by Lovable are read-only; never rewrite their history
- If you need to revert Lovable changes, create a new commit
- Communicate design changes needed via PR comments, not code rewrites

### Code Quality Gates

**Before merge:**
- `bun run lint` must pass (ESLint + Prettier)
- `bun x tsc --noEmit` must pass (TypeScript strict mode)
- `bun run build` must succeed
- `bun run dev` must start without errors
- Visual regression checks (Lovable lead)

### Secrets and Security

**Server-side only (never in client code):**
- `OPENROUTER_API_KEY` — AI provider access
- `SUPABASE_SERVICE_ROLE_KEY` — database admin access
- Database connection strings
- OAuth credentials

**Client-safe only:**
- `SUPABASE_URL` — public Supabase endpoint
- `SUPABASE_ANON_KEY` — public anonymous key
- Analytics tokens (no PII)

**Never commit:**
- `.env` files
- Private keys or credentials
- Database dumps
- API responses with PII

### No Manual Edits
- `src/routeTree.gen.ts` is auto-generated; never edit manually
- `src/integrations/supabase/*` is generated by Lovable Cloud; do not modify
- Regenerate via Lovable Cloud UI or documented scripts only

### API and Contract Changes
- API routes, types, and contracts must be defined in code, not via visual tasks
- Breaking changes require planning; coordinate via issues/PRs
- Type safety is required; no `any` types in contracts

### Infrastructure as Code
- Render configuration is version-controlled in Git
- Database migrations are SQL files in `migrations/` with timestamps
- No infrastructure changes via UI; all via code and review

### Limitations and Principles
- No RAG (Retrieval-Augmented Generation) without demonstrable need
- No Redis, task queues, or background workers without architecture review
- No LangChain, LangGraph, or AI framework lock-in without decision record
- No microservices; full-stack TanStack Start by default (backend separation only if justified by scale/complexity)
- Incremental refactor only; no big-bang rewrites
- See RCKT Principle in docs/knowledge/07-change-policy.md for architectural decision framework
