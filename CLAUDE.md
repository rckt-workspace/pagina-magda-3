# Claude Code Guidelines for pagina-magda-3

This document defines how Claude Code should approach work in this repository.

## Project Context

**Magda** is a professional services website built with:

- **Stack**: TanStack Start + React 19 (full-stack, visual-first via Lovable Cloud)
- **Server Routes**: TypeScript handlers in `src/routes/api/*` for business logic
- **Data**: Supabase PostgreSQL (auth, leads, metrics, observability)
- **AI**: OpenRouter integration (server-side, in TanStack Start routes)
- **Deployment**: Single Render Web Service (one repo, one build, one deploy)

The project is visual-first and design-driven. Lovable Cloud owns the presentational layer; Claude Code owns server routes and integrations within the same TanStack Start project.

## Known Technical Debt

1. **HTML + DOM Imperative**: `src/routes/-site-content.ts` contains injected HTML with DOM manipulation
   - No refactor yet; leave as-is
   - Future: migrate to React component tree
   - Reason: Lovable Cloud edit feedback loop requires stability

2. **Supabase Auth in Start**: Auth middleware is in `src/integrations/supabase/`
   - Generated by Lovable Cloud; do not modify
   - Current design: authentication stays in TanStack Start (no auth gateway needed)

3. **No Incremental Static Regeneration (ISR)**: Each page is fully dynamic
   - Current: Dynamic rendering (acceptable for current deployment)
   - Future: ISR for marketing pages if scale/performance requires optimization

4. **CSS in Public**: `public/site.css` is hand-crafted and extensive
   - Lovable Cloud preserves it on exports
   - Leave untouched; coordinate changes via design branch

## Implementation Strategy

**Core principle: Incremental, modular, no big-bang rewrites.**

All server logic lives in TanStack Start (`src/routes/api/*`), deployed as one Render Web Service.

### Phase 1 (Current): Foundation

- Establish governance (AGENTS.md, CLAUDE.md, docs/knowledge/)
- Database schema (`public.leads`, `public.llm_usage`)
- Server routes architecture (services + providers pattern)
- Keep frontend stable via Lovable Cloud

### Phase 2: Server Routes & Services

- Implement `src/routes/api/leads.ts` (POST, validation, Supabase)
- Implement `src/routes/api/chat.ts` (POST, OpenRouter, llm_usage logging)
- Service layer (ChatService, LeadService)
- Provider pattern (OpenRouterProvider, SupabaseProvider)
- No heavy dependencies (no LangChain, no RAG yet)

### Phase 3: Observability & Metrics

- Implement `src/routes/api/metrics.ts`
- Wire llm_usage logging from chat route
- Monitoring/alerting for performance

### Phase 4: Scale & Polish

- Performance optimization if needed
- Additional AI features (if justified by use)
- Caching strategy (if warranted)
- Admin/dashboard UI (if needed)

## Architectural Constraints

### What to NEVER Do

- **No big-bang rewrites** — every change must be incremental and reviewable
- **No new frameworks** — no Next.js, Nuxt, SvelteKit (we own TanStack Start)
- **No Lovable Cloud schema edits** — don't touch `src/integrations/supabase/*`
- **No manual routeTree edits** — never touch `src/routeTree.gen.ts`
- **No RAG, Redis, or task queues** — until demonstrable need with architecture review
- **No LangChain or LangGraph** — use OpenRouter API directly; no framework lock-in
- **No separate FastAPI backend** — all server logic lives in TanStack Start `src/routes/api/*`
- **No secrets in client code** — OPENROUTER_API_KEY, SUPABASE_SERVICE_ROLE_KEY stay server-side only

### What to DO

- **Review AGENTS.md** before any structural change
- **Use TypeScript strict mode** — no `any`, no unsafe casts
- **Write decision records** — when adding major dependencies or patterns
- **Test locally first** — `bun run dev` before pushing
- **Lint and typecheck** — `bun run lint`, `bun x tsc --noEmit`
- **Atomic commits** — one logical change per commit
- **Communicate via PRs** — no direct pushes to main

## Secrets and Environment

**Production Secrets (Render Web Service):**

- `OPENROUTER_API_KEY` — Lives in Render dashboard, never commit
- `SUPABASE_SERVICE_ROLE_KEY` — Lives in Render, never commit

**Public Config (in repo):**

- `SUPABASE_URL` — Public Supabase endpoint
- `SUPABASE_ANON_KEY` — Public anonymous key

**Local Development:**

- Create `.env.local` (in `.gitignore`)
- Copy keys from Render dashboard or Supabase project settings
- `bun run dev` loads `.env.local` automatically

## Code Quality Checklist

Before pushing or requesting review:

- [ ] `bun run lint` passes (ESLint + Prettier)
- [ ] `bun x tsc --noEmit` passes (TypeScript)
- [ ] `bun run build` succeeds
- [ ] `bun run dev` starts without errors
- [ ] No changes to Lovable-owned files (unless coordinating design change)
- [ ] No manual edits to `src/routeTree.gen.ts` or `src/integrations/supabase/*`
- [ ] No secrets in code (run `grep -r "sk_" src/ || echo "OK"`)
- [ ] Commit message references the GitHub issue or PR
- [ ] No force push to main or published branches
