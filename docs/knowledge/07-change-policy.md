# Change Policy

## Overview

This document defines how changes flow through the project, from idea to production.

**Core Principle**: All changes go through Git. No exceptions.

## RCKT Architecture Principle

**Full-stack by default; backend separation only if justified.**

Magda uses a **full-stack TanStack Start architecture** by default:
- Server routes in `src/routes/api/*` handle all business logic
- Services layer (`src/services/*`) manages domain operations
- Providers layer (`src/providers/*`) handles infrastructure (OpenRouter, Supabase)
- **Single Render Web Service** deployment (no microservices overhead)

**Why full-stack by default?**
- Simpler operations (one service, one deploy, one failure domain)
- Faster development (no inter-service communication latency or complexity)
- Better for light to medium projects (Magda's scope)
- Easier debugging (full stack in one runtime)
- Clearer limits (when monolith gets too complex, refactor with data)

**Backend separation is allowed only if:**
1. **Data scale** justifies separate database (e.g., separate analytics store)
2. **Operational complexity** proves monolith is unmanageable (metrics and monitoring needed first)
3. **Technical requirement** demands different runtime (e.g., background workers for long-running jobs)
4. **Explicit decision record** exists documenting the trade-off

**This applies to any major change:**
- ❌ "We should use FastAPI" — No, unless above conditions met
- ❌ "We should add Redis" — No, until in-process state is proven insufficient
- ❌ "We should use a message queue" — No, until synchronous calls are proven inadequate
- ✅ "We're hitting rate limits with OpenRouter" — Yes, archive old data to separate table
- ✅ "Leads table has 10M rows and queries are slow" — Yes, consider data separation with documented decision

### Line Ending Handling (CRLF vs LF)

Windows developers and Lovable Cloud may have different line ending preferences (CRLF vs LF).
To avoid false diffs:

- `.prettierrc` is configured with `"endOfLine": "auto"`
- This tells Prettier to preserve the platform's line endings
- **No mass normalization** (`git add --renormalize`) will be performed
- Repository maintains mixed LF (Git) and CRLF (Windows working trees) without forced conversion
- This avoids thousands of false line-ending changes blocking code review

### ESLint Rule Exceptions (Temporary)

Two files have specific ESLint rule overrides due to their lifecycle stage:

**1. `src/integrations/supabase/types.ts`**
- Override: `prettier/prettier` disabled
- Reason: Auto-generated by Lovable Cloud; formatting enforced by generator
- Lifecycle: Temporary while Lovable integration is active
- Removal: Delete override when Lovable-generated schema is no longer needed

**2. `src/routes/-site-content.ts`**
- Override: `no-useless-escape` disabled
- Reason: Legacy HTML injection with complex regex patterns
- Lifecycle: Will be eliminated during frontend refactoring (Phase 5)
- Removal: Delete override when component migrates to React tree

**Policy**: These overrides are NARROW and specific. They do NOT represent a relaxation of project code quality standards. Each override documents its exit condition and will be removed when that condition is met.

## Branch Structure

### Main Branch

**Branch Name**: `main`  
**Protection**: Yes (reviewed PRs only)  
**Deployment**: Automatic to Render (on push)  
**Frequency**: Multiple times per day (expected)

**What can merge**:

- Reviewed pull requests
- No direct pushes
- All checks must pass (lint, typecheck, build)

**What must NOT merge**:

- Work-in-progress code
- Secrets or credentials
- Breaking changes without migration
- Commits from unknown authors

### Design Branch

**Branch Name**: `design/*` (e.g., `design/hero-refresh`)  
**Owner**: Lovable Cloud  
**Purpose**: Visual design iterations, animations, copy updates  
**Lifetime**: Temporary (usually 1–3 days)

**What's in design branches**:

- Layout changes
- Color and typography updates
- Animations and micro-interactions
- Asset additions (images, icons)
- Approved copy changes

**What's NOT in design branches**:

- API contract changes
- Backend logic
- Database migrations
- Type definition changes
- Environment configuration

**Merge Path**: `design/xyz` → Pull Request → Review by both teams → Merge to `main`

### Feature Branch

**Branch Name**: `feature/*` (e.g., `feature/llm-integration`)  
**Owner**: Claude Code  
**Purpose**: Backend features, integrations, architecture  
**Lifetime**: Days to weeks (single feature)

**What's in feature branches**:

- Backend features (server routes in TanStack Start)
- Database migrations
- New API endpoints or server functions
- Type definitions and contracts
- Security and configuration changes

**What's NOT in feature branches**:

- Visual design changes (request via design branch)
- Large refactors without issue (create issue first)
- Experimental code (use separate branch)

**Merge Path**: `feature/xyz` → Pull Request → Review by tech lead → Merge to `main`

### Fix Branch

**Branch Name**: `fix/*` (e.g., `fix/form-validation`)  
**Owner**: Either team  
**Purpose**: Bug fixes, small corrections  
**Lifetime**: Hours to days (single bug)

**What's in fix branches**:

- Bug fixes (frontend or backend)
- Hotfixes for production issues
- Typo corrections
- Dependency security updates

**What's NOT in fix branches**:

- New features (use feature branch)
- Refactoring (use feature branch)
- Multiple bugs (create separate fix branches)

**Merge Path**: `fix/xyz` → Pull Request → Review (expedited) → Merge to `main`

### Experimental Branch

**Branch Name**: `exp/*` or `sandbox/*`  
**Owner**: Any team  
**Purpose**: Exploration, research, prototypes  
**Lifetime**: Days to weeks (then delete)

**What's in exp branches**:

- Prototype code
- Performance experiments
- Architecture exploration
- POCs and investigations

**What's NOT in exp branches**:

- Production code (must eventually go to feature/*)
- Secrets or credentials

**Merge Path**: Usually NOT merged to main (delete after research)

## Pull Request Workflow

### Creating a Pull Request

**Before creating PR**:

1. Branch is up-to-date with `main`

   ```bash
   git fetch origin
   git rebase origin/main
   ```

2. All checks pass locally

   ```bash
   bun run lint          # No lint errors
   bun x tsc --noEmit    # No type errors
   bun run build         # Build succeeds
   ```

3. Commit messages are clear

   ```bash
   git commit -m "feat: add contact form email field"
   git commit -m "fix: correct scroll reveal timing"
   git commit -m "refactor: simplify server middleware"
   ```

4. No secrets in code
   ```bash
   grep -r "sk_" src/ || echo "OK"
   grep -r "password" src/ || echo "OK"
   ```

### Review Process

**For `design/*` PR**:

1. **Lovable Cloud** submits PR (with screenshots/preview)
2. **Claude Code** reviews for:
   - No API contract changes
   - No backend logic changes
   - No `package.json` modifications
   - No type definition changes
3. **Merge** (if approved)

**For `feature/*` PR**:

1. **Claude Code** submits PR (with issue link)
2. **Tech Lead** reviews for:
   - Architecture alignment
   - No big-bang rewrites
   - Test coverage (if applicable)
   - Documentation (CLAUDE.md, docs/knowledge/)
3. **Lovable Cloud** reviews (if visual impact)
4. **Merge** (if approved by tech lead + Lovable, if needed)

**For `fix/*` PR**:

1. **Author** submits PR
2. **Any reviewer** can approve (expedited)
3. **Merge** (fast-track)

**Approval Requirements**:

- ✅ At least 1 approval
- ✅ All CI checks pass (lint, typecheck, build)
- ✅ No merge conflicts
- ✅ Conversation resolved

### Merging

**Standard Merge** (default):

```bash
git merge --ff-only origin/feature/xyz
```

Creates a merge commit (linear history).

**Never Use**:

- ❌ `git merge --squash` (hides commits)
- ❌ `git rebase` (if commits are published)
- ❌ `git push --force` (rewrites history)

**After Merge**:

- PR shows as "Merged"
- Branch is deleted automatically (GitHub setting)
- Render auto-deploys to production

## Conflict Resolution

### If Main and Branch Conflict

**Before merging PR**:

1. **Update branch**:

   ```bash
   git fetch origin
   git rebase origin/main
   ```

2. **Fix conflicts**:
   - Open conflicted files in editor
   - Resolve conflicts (keep both sides if needed)
   - Test locally

3. **Continue rebase**:

   ```bash
   git add .
   git rebase --continue
   ```

4. **Force-update PR** (only if rebase was local):
   ```bash
   git push origin feature/xyz --force-with-lease
   ```

### If Visual + Backend Conflict

**Example**: Lovable updates form layout, Claude adds email field

**Resolution**:

1. Claude submits `feature/contact-email` PR
2. Lovable submits `design/contact-redesign` PR
3. **Communication**: Comment on PRs ("I'm waiting for your PR to merge first")
4. Claude merges first → `feature/contact-email` to main
5. Lovable rebases: `design/contact-redesign` on new main
6. Lovable re-designs to account for new email field
7. Lovable merges → `design/contact-redesign` to main

## Commit Guidelines

### Format

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Types**:

- `feat` — New feature
- `fix` — Bug fix
- `refactor` — Code refactoring (no new features, no bug fixes)
- `docs` — Documentation only
- `style` — Formatting, linting (no code logic change)
- `test` — Test additions/updates
- `chore` — Dependencies, config, tooling
- `perf` — Performance improvement

**Examples**:

```
feat(contact-form): add email field validation
fix(hero): correct scroll reveal animation timing
refactor(api): simplify server middleware
docs(deployment): update Render configuration
```

### Subject Line Rules

- Imperative mood ("add", not "added")
- No period at end
- Max 50 characters
- Lowercase (except proper nouns)

### Body Rules

- Explain **why**, not what
- Wrap at 72 characters
- Separate from subject with blank line

**Example**:

```
fix(form-submit): prevent double submissions

Users could click submit button multiple times quickly,
causing duplicate leads. Add debounce to button handler
to prevent this.

This was reported in issue #42 by [user].
```

### Linking Issues

In PR or commit:

- `Closes #123` — Close issue automatically when PR merges
- `Fixes #456` — Same as above
- `Related to #789` — Reference without closing

## Rollback Policy

### If Merge Breaks Production

1. **Identify**: Check Render logs for error
2. **Assess**: Is it critical or can it wait?
3. **Rollback**: If critical:

   ```bash
   git revert <commit-hash>
   git push origin main
   ```

4. **Create Issue**: Track the problem
5. **Fix**: Create new PR with fix
6. **Re-merge**: Once fixed and tested

### Automated Rollback (Future)

If we add health checks or monitoring:

- Render can auto-rollback if health check fails
- Alert sent to team
- Incident created

## Release Management

### Version Strategy

Use semantic versioning in Git tags:

- `v1.0.0` — Initial release
- `v1.1.0` — Features added
- `v1.1.1` — Bug fix only
- `v2.0.0` — Breaking changes

### Tag Command

```bash
git tag -a v1.0.0 -m "Release: v1.0.0"
git push origin v1.0.0
```

### Release Notes

Create GitHub Release (one per tag):

- Copy commit history since last tag
- Summarize changes by type (features, fixes, etc.)
- Thank contributors

## Review Checklist

**Before Approving PR**:

- [ ] **Correctness**: Code does what PR claims
- [ ] **Quality**: Follows style guide, no code smells
- [ ] **Tests**: New code is tested (if applicable)
- [ ] **Documentation**: Changes are documented
- [ ] **Security**: No secrets, no vulnerabilities
- [ ] **Performance**: No obvious slowdowns
- [ ] **Accessibility**: UI changes are accessible
- [ ] **Compatibility**: Doesn't break existing features
- [ ] **Lovable Sync**: No unintended visual changes (if backend PR)

## Prohibited Actions

### Never

- ❌ Push directly to `main` (always use PR)
- ❌ Force push after merge
- ❌ Rewrite published commits (`git rebase -i` on main)
- ❌ Merge without CI passing
- ❌ Merge unreviewed code
- ❌ Commit secrets (check before pushing)
- ❌ Approve your own PR
- ❌ Merge with open conversations

### Escalation

If someone breaks these rules:

1. **Revert** the commit immediately
2. **Discuss** in issue or meeting
3. **Document** what happened (for lessons learned)
4. **Update** AGENTS.md or this policy if pattern repeats
